1. Executive Summary & Product Vision

LazyLayout (internally designated "Unreal Engine for Animation & Frontend Design" and "Figma for Motion with AI") is an AI-native motion design studio. It bridges the deep gulf between three disciplines that rarely overlap: visual motion design, animation engineering (GSAP, Framer Motion, WAAPI, Three.js, shaders), and production-grade frontend engineering.

In standard industry workflows, designers create animations in Figma or After Effects that cannot be cleanly translated to code without manual rewriting, approximation, and performance degradation. Conversely, frontend developers write complex animation scripts without interactive visual feedback. LazyLayout resolves this by providing:

  • A unified visual canvas that feels like Figma for authoring responsive layouts, vector shapes, typography, and design tokens.
  • A multi-engine animation timeline that operates like After Effects (with keyframe twirl-downs, stopwatches, curves, and transport control).
  • A deterministic evaluation kernel (evaluate(t)) guaranteeing that what you scrub and play in the editor matches exported production code down to the sub-pixel (Preview = Export).
  • Multi-target static code generation compiling to production Next.js 16 (App Router), Vite + React, or standalone HTML with Tailwind, CSS Modules, or vanilla CSS.
  • AI-native authoring where Claude API or local MCP agents can propose layout and motion changes as typed, reviewable diffs with strict zero-silent-write guarantees.
Current Repository State (October 2026): The repository is operating under ROADMAP v4.0.0 (202 sequential phases). Stage 0 (Phases 1–12) is 100% complete. Stage 1 (Phases 13–52) has delivered the complete viewport, drawing tools, inspector, design tokens, components, multi-page routing, and static export (with active FigCraft port deepening F1–F14). Stage 2 (Phases 53–102) has merged Phases 53–63 to main, delivering schema v6, central clock transport, frame scheduler, WAAPI acceleration, and the Layer Timeline.

4. Architectural Subsystems Breakdown

4.1 Unified Motion Document Model (MDM v6)

The core data model lives under src/core/document/. It defines 216 canonical property paths organized into a strictly typed document tree:

// Conceptual Document Hierarchy
MotionDocument {
  id: string,
  schemaVersion: 6,
  pages: Record<string, Page>,
  layers: Record<string, Layer>,            // Flat dictionary of all layers with parentId links
  compositions: Record<string, Composition>,// Timeline tracks, triggers, work areas, markers
  clips: Record<string, Clip>,              // Keyframe sequences, behaviors, reactive signals
  designComponents: Record<string, Component>, // Component definitions, variants, properties
  tokens: { collections, variables, modes },// Design tokens and semantic color/number variables
  breakpoints: Breakpoint[],               // Responsive breakpoints (Desktop, Tablet, Mobile)
  assets: Record<string, Asset>             // Image/font asset registry with SHA-256 deduplication
}

Every property is accessed via dot-notation canonical paths (e.g. transform.x, appearance.opacity, paint.fills, shape.cornerRadius, layout.auto). All mutations occur through patch-based command transactions that create atomic undo/redo records in IndexedDB.

4.2 Command Bus & Focus Model (Phase 13)

Located in src/core/commands/. Every interactive action is a typed command registered with a unique identifier (e.g. edit.undo, canvas.zoomIn, transport.play, tool.select). Commands specify VS Code-style when context clauses reading from the Zustand context keys store:

  • canvasFocus: True when pointer hovers the stage canvas.
  • timelineFocus: True when pointer hovers the Layer Timeline or Sequencer.
  • textEditing: True when an input, textarea, or canvas inline text editor has focus.
  • selection.count: Number of currently selected layers.
  • transport.playing: Whether the animation transport is running.

This completely eliminates keyboard shortcut conflicts (e.g. pressing Space over the timeline plays animation, while pressing Space over canvas activates the Hand panning tool).

4.3 Stage Host v2 & DOM Isolation (Phase 18)

Prior to Phase 18, the editor stage was an HTML string injected into an iframe (srcDoc), causing the entire canvas to reload on every keystroke. StageHost v2 mounts a permanent, static iframe (/stage-frame.html) governed by strict Content Security Policy (script-src 'none'):

  • The iframe never runs untrusted scripts or eval.
  • Mutations are reconciled incrementally via DOM operations using LayerNodeRegistry (Phase 19).
  • Editing a layer's color, position, or size updates only that specific DOM node in under 1ms, maintaining smooth 60 FPS even with 500+ complex layers.

4.4 Dual Animation Engine & Parity Verification (Phases 57–60)

LazyLayout solves the classic animation editing paradox (scrubbing requires instant random-access mathematics, while playback requires hardware-accelerated thread independence) using a dual-engine architecture:

  • Scrubbing & Paused State: The pure TypeScript Deterministic Evaluation Kernel (src/core/kernel/evaluate.ts) evaluates all property paths at exact time t. It integrates GSAP-derived cubic-bezier easings and Framer Motion physical spring formulas.
  • Playing State: Eligible CSS properties (transforms, opacity, colors) hand off instantly to native browser Web Animations (WAAPI) running on the compositor thread.
  • Zero-Pixel Handoff: Pausing terminates WAAPI and re-applies kernel inline styles with 0.0px jump.
  • Parity Badge: A real-time drift auditor (src/core/engine/stage/parity.ts) samples the stage every 30 frames and computes mathematical variance against evaluate(t). A green badge in the status bar confirms drift remains under 0.5px.

4.5 FigCraft Port Architecture (F1–F14)

On branch a/figcraft-port, LazyLayout incorporates the engine algorithms from the high-performance Rust vector engine FigCraft (MIT licensed), translating data structures and mathematical behaviors into clean TypeScript:

  • Squircle Corner Smoothing (F1): Continuous-curvature corner radii (G2 continuity) rather than simple circular arcs.
  • Display P3 Color Gamut (F2): Full wide-gamut color parsing and color(display-p3 ...) rendering.
  • Vector Networks & Paint Bucket (F4): True non-manifold vector topologies with vertices, segments, and faces, editable via the Paint Bucket tool (B).
  • Live Boolean Groups & Shape Builder (F5): Non-destructive boolean unions/subtractions where operands remain editable layers, plus the interactive Shape Builder tool (Shift+M).
  • Dev Mode (F13): Inspector showing CSS syntax with token variables, annotations, and kept measurement overlays.

1. Manual Testing Methodology & The "Do → Expect → Fails if" Standard

To ensure 100% test reproducibility across human testers, automated agents, and multi-browser environments, every test in this guide adheres to the rigorous Do → Expect → Fails if tripartite formula:

  • Do: The exact sequence of physical user interactions—keystrokes, mouse moves, clicks, drags, or menu selections.
  • Expect: The precise observable visual, temporal, or DOM state that must occur if the implementation is correct.
  • Fails if: Explicit descriptions of bug states, regressions, timing drift, visual artifacts, or console errors that constitute an immediate test failure.

1.1 Defect Logging & Write-In Protocol

CRITICAL QA INSTRUCTION: Every test case includes a status selector (Pass, Fail, Blocked) and a dedicated ✎ Actual Outcome / Defect Notes write-in box. If what you observe matches the Expect specification exactly, mark [X] Pass. If the expected outcome was NOT observed, or if unexpected behavior occurred:
  1. Mark [X] Fail (or [X] Blocked if preceding steps prevent reaching this state).
  2. In the provided write-in lines, explicitly record:
    • What actually appeared on screen or failed to appear.
    • The exact text of any Red Console Errors in DevTools.
    • Browser name, version, and operating system.
    • Whether running in npm run dev or a production build (npm run build && npm run start).
