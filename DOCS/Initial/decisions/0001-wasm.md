# Decision 0001: C++/WebAssembly Kernel — No-Go

**Status:** Decided **No-Go**. **Date:** 2026-09-25. **Owner:** ROADMAP Sub-Phase 5.3 (`DOCS/Initial/ROADMAP.md`), closes AUD-10, AUD-11, AUD-12.

## Decision rule (from ROADMAP Sub-Phase 5.3)

> Keep Wasm only if it is ≥ 2x faster on a workload the product actually runs per frame. Otherwise remove the build step, keep the TS code, and archive `wasm/`.

The benchmark below never reliably clears that bar. **Wasm is removed.** The archived C++ source lives at `DOCS/Initial/decisions/0001-wasm-archive/` (not built by anything); the TypeScript implementations (`src/core/wasm/SplineSolver.ts`, `CablePhysics.ts`, `SpatialIndex.ts`) are the permanent, sole implementation. `npm run build:wasm` no longer exists.

## What was found before any benchmark was possible

The C++ kernel had **never actually compiled**, on any commit, going back to when it was first written:

- `SplineSolver.cpp` used `v128_t`/`wasm_f32x4_*` SIMD intrinsics without including `<wasm_simd128.h>` — undefined identifiers, a hard compile error.
- `WasmBindings.cpp` had `using namespace emscripten;` but never `using namespace WebAppEngine;`, so every type it binds (`AABB`, `SplineConfig`, `SplineResult`, ...) was unqualified and unresolvable.
- Past that: `WasmBindings.cpp` bound methods and fields that don't exist on the current headers at all — `SplineResult::totalArcLength` (it's `approximateLength`), `SplineSolver::getTForNormalizedArcLength` and `::sampleEquidistantPoints` (they're `ArcLengthTable::getTForNormalizedArcLength` and `SplineSolver::sampleUniformPoints`), `SpatialIndex::hitTestTopmost` called with the wrong arity (it takes an out-param, not a return value), and a `WireType` enum with entirely different member names (`EXEC`/`DATA_BOOL`/... vs. the header's `Exec`/`DataBoolean`/...). This is not drift from a recent header change — the bindings and the headers were never consistent with each other.
- **There is no C++ implementation of spring baking at all.** ROADMAP Sub-Phase 5.3 names "spline evaluation, path arc-length sampling and spring baking" as the three things to benchmark; only the first two exist in `wasm/` (now the archive). Spring easing/baking (the damped harmonic oscillator work in `AnimationLoweringCompiler.ts`, Phase 9.1) has no C++ counterpart to compare against, so it isn't part of this benchmark — it can only ever be TypeScript.

All of the above were fixed (see the archived source's `src/WasmBindings.cpp` and `src/SplineSolver.cpp`) to get a working build at all, purely so this decision could be made on real evidence instead of on the assumption that a working kernel was one `make release` away. `WasmBridge.getSplineSolver()` additionally never routed calls to a loaded Wasm module even when one loaded successfully — it always called the static TS `SplineSolver` — so before today, **100% of this math has always run as TypeScript in the shipped app**, regardless of anyone's belief about the "C++ Wasm" badge in the UI (AUD-11: that badge was hardcoded to claim a link that never existed; fixed alongside this decision).

## Benchmark

**Method:** real Chromium (Playwright's `chromium.launch()`, not jsdom/node), `DOCS/Initial/decisions/0001-wasm-archive/benchmark/{bench.html,run-bench.mts}`. Emscripten 6.0.10 (`-O3 -flto -msimd128`), Node 24-class V8 for the TS side (same browser process). 20 warmup frames + 60 timed frames per path, `performance.now()` per frame, median reported (least sensitive to GC/JIT outliers).

**Workload:** 200 wires (ROADMAP's own sizing: "200 tracks × 120 samples"), each requiring a spline calculation plus a 120-sample arc-length table plus a 12-point uniform sample — the per-frame shape `WasmCableCanvas.tsx`/the Blueprint canvas actually needs.

Two call patterns, both real API surfaces of this codebase:

1. **Per-wire calls** — `SplineSolver.calculateWireSpline()` / `buildArcLengthTable()` / `sampleUniformPoints()` called once per wire (3 JS↔Wasm boundary crossings × 200 wires). This is what `WasmBridge.getSplineSolver()`'s individual methods do.
2. **Batched call** — `calculateBatchSIMD()` / `calculateBatchVectorized()`, one call for all 200 wires (1 boundary crossing total). This is `WasmBridge.getSplineSolver().calculateBatchSplines(wires, useSimd=true)`'s path, and the best case for Wasm (marshalling cost amortized over the whole batch).

5 runs each, same machine, same process warm:

| Run | Per-wire: TS median (ms) | Per-wire: Wasm median (ms) | Per-wire speedup (TS/Wasm) | Batch: TS median (ms) | Batch: Wasm median (ms) | Batch speedup (TS/Wasm) |
|---|---|---|---|---|---|---|
| 1 | 1.3 | 2.1 | 0.62x | 1.2 | 0.6 | 2.00x |
| 2 | 1.6 | 2.0 | 0.80x | 1.1 | 0.6 | 1.83x |
| 3 | 1.4 | 1.8 | 0.78x | 1.3 | 0.6 | 2.17x |
| 4 | 1.3 | 2.5 | 0.52x | 1.3 | 0.6 | 2.17x |
| 5 | 1.4 | 2.2 | 0.64x | 1.2 | 0.8 | 1.50x |
| **mean** | | | **0.67x** | | | **1.93x** |
| stdev | | | 0.12 | | | 0.28 |

**Per-wire (the realistic call pattern): Wasm is *slower* than TypeScript**, by about 1.5x, consistently across every run (0.52x–0.80x, never once above 1.0x). Small, frequent JS↔Wasm boundary crossings — each carrying a `Point2D`/`SplineConfig`/`SplineResult` (with a `std::string` SVG path and a `std::vector<float>` arc-length table) through embind's marshalling — cost more than V8 saves by not running the equivalent TS.

**Batched into a single call (Wasm's best case): mean 1.93x, never reliably ≥ 2x.** Only 3 of 5 runs even touched 2.0x; the range (1.50x–2.17x) straddles the bar entirely on run-to-run noise. This is with the batch entry point every caller would have to be rewritten to use consistently — most of the app calls the per-wire methods today.

## Why this isn't "just needs more tuning"

- The marshalling overhead is structural to embind's `value_object` copying (strings, vectors, and structs are all copied across the boundary on every call), not a compiler-flag problem. Clearing 2x reliably would need typed-array/`SharedArrayBuffer` transfer for the hot path (registers as a much larger rewrite of both the C++ API and every caller) — exactly the kind of investment Phase 5's evidence-based framing exists to gate.
- The workload here (200 splines/frame) is already toward the high end of what a single Blueprint canvas or Sequencer view shows at once; there's no larger "the C++ would obviously win at scale" case sitting just past this benchmark's size, since even the batched, single-crossing best case caps out under 2x at this size.
- Spring baking, one of the three named benchmark targets, isn't implemented in C++ at all and never was — there's nothing to benchmark there, and building it now (to service a kernel that just failed its own bar for the workloads it does support) isn't justified.

## What changed as a result

- `wasm/` → `DOCS/Initial/decisions/0001-wasm-archive/` (C++ source, headers, `CMakeLists.txt`, `Makefile`, the benchmark harness that produced the numbers above). Its own `dist/` build output is gitignored, as before.
- `package.json`: removed the `build:wasm` script.
- `.gitignore`: wasm-specific ignore rules updated to the archive path.
- `src/core/wasm/{WasmBridge,SplineSolver,WasmWorkerPool}.ts`: doc comments updated from "the go/no-go call is Sub-Phase 5.3" (open question) to recording this decision. The dual-backend fallback code in `WasmBridge.ts` is kept as-is — it already reports `backend: "typescript"` honestly and costs nothing at runtime, so there's no correctness reason to rip it out, only to stop describing it as pending.
- `src/editor/shell/StudioHeader.tsx`: the header badge no longer branches on a Wasm backend that can now never activate — it's a static, honest "TypeScript 120 FPS" (was previously hardcoded to falsely claim "C++ WebAssembly Engine linked", AUD-11).
- `src/editor/panels/settings/ProjectSettings.tsx`: removed the "Wasm Kernel Optimization Level" dropdown entirely (`-O3`/`-O2`/`-O0`). It never did anything before this decision (dead local state, read by no build); after this decision it's not merely unwired, it's permanently inapplicable.
- `src/editor/panels/curves/CurveEditor.tsx`: same doc-comment update (was already fixed to not claim Wasm as part of Sub-Phase 5.2; now records the concluded decision).

## Revisiting this decision

Would need, at minimum: (1) the hot path rewritten to move data across the boundary via a shared `ArrayBuffer`/`SharedArrayBuffer` instead of per-call `value_object` marshalling, and (2) every caller (not just a batch-capable subset) actually using the batched entry points, since the per-wire pattern is not just slower but the app's *default* pattern today. Absent both, re-running this exact benchmark would be expected to reproduce the same result.
