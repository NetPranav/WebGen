# Decision 0007: Phase 9 — The Deterministic Evaluation Kernel

**Status: ✅ Phase 9 complete — Verification Gate passed 2026-09-26.** **Owner:** ROADMAP Phase 9. **Code:** `src/core/kernel/` (`easing.ts`, `springs.ts`, `color.ts`, `interpolators.ts`, `evaluate.ts`).

Phase 9's goal: a pure function gives the exact value of any animated property at any time, for any inputs — the oracle for preview, export parity, AI verification and scrubbing. This record is the numbering AUDIT.md's own §5.2 note anticipated: "Pure math modules [SplineSolver, PathMorphSolver, Scene3DEngine, AnimationLoweringCompiler]... become the deterministic `evaluate(t)` kernel in Phase 9" — this phase is that assembly, not a rewrite of any of them.

**Verification Gate, checked 2026-09-26:**
- Golden-value tests for every easing and interpolator against reference implementations — `src/core/kernel/__tests__/easing.test.ts` (58 assertions) compares every named GSAP family/direction against the real, installed `gsap` package's own `gsap.parseEase(...)`, not a hand-derived approximation; `cubic-bezier()` and `steps()` follow the CSS Easing spec algorithms, checked against a brute-force bisection oracle and the spec's own worked boundary cases; `springs.test.ts` (14 assertions) checks the perceptual→physical conversion against the real, installed `motion` package's own spring generator; `color.test.ts` (11) checks OKLab against its defining invariants (white/black) and round-trip identity; `interpolators.test.ts` (16) checks every `InterpolationMethod` `PROPERTY_REGISTRY` already declares (Phase 7.1).
- Fuzz test: evaluation is deterministic (same inputs → same bytes) — `evaluate.test.ts`, 200 random `(t, inputs)` samples over a document with clips, a state, and a behaviour, each evaluated twice and compared byte-for-byte (`JSON.stringify` equality).

## 1. What Phase 7 had already built, reused rather than duplicated

`motion.ts`'s `parseEasing` already turns every easing string into structure (`Easing` discriminated union) and `SpringSchema` already types both the perceptual `{bounce, time}` and physical `{stiffness, damping, mass?}` faces (Law 17) — both explicitly commented "the kernel (Phase 9.1) gives it structure/evaluates it". `properties.ts`'s `PROPERTY_REGISTRY` already classifies every canonical path into one of exactly the 8 `InterpolationMethod`s 9.2 asks for (numeric/color/path/clipPath/vector/slerp/gradient/discrete), with a comment naming Phase 9.2 for the colour case specifically. `compositions.ts` (Phase 46) already has the full composition-time math (`layerTime`, `clipTimeInComposition`, nesting, remap). Phase 9's job was the missing piece each of these was built anticipating: the *numeric evaluator*.

## 2. Easing (9.1): ported from GSAP's own source, not re-derived

Named-family formulas (power0-4, quad/cubic/quart/quint/strong, sine, circ, expo, back, elastic, bounce) are transcribed line-for-line from `gsap-core.js`'s `_insertEase`/`_configBack`/`_configElastic` (reading the actual installed dependency's source, not reconstructing from memory), then verified against `gsap.parseEase(...)`'s live output rather than trusting the transcription alone. `cubic-bezier()` uses the standard Newton-Raphson/bisection solver (the same algorithm every browser uses for CSS). `steps()` follows CSS Easing Level 1 §4 (`start`/`end`/`none`/`both` jump terms). A spring used as a keyframe's easing gets a concrete duration from its own settling time (`springSettlingTime`), so `sampleEasing` answers "progress at t ∈ [0,1]" uniformly across every easing kind.

## 3. Perceptual springs (9.1, v3.2): the conversion is Motion's own formula

The `{bounce, time}` → `{stiffness, damping, mass}` conversion is ported from Motion's `spring.mjs` (`getSpringOptions`'s `visualDuration` branch: `naturalFreq = 2π/(time×1.2)`, `stiffness = naturalFreq²`, `damping = 2×clamp(0.05,1,1−bounce)×√stiffness`), per the ROADMAP's explicit instruction to check this against Motion's own `bounce`/`visualDuration` so a Motion export feels the same. The analytic under/critically/over-damped integrator (`evaluateSpring`) is self-derived from the boundary conditions `x(0) = origin`, `x'(0) = initialVelocity` — this is what gives "velocity handoff" (an interrupted spring's outgoing velocity becomes the next one's starting velocity, so retargeting mid-flight never pops) — and cross-checked against Motion's real generator's value curve at multiple `(bounce, time)` pairs, not just self-consistency.

## 4. Interpolators (9.2): the classification already existed; this is its evaluator

`interpolateValue(method, from, to, t)` dispatches on `PROPERTY_REGISTRY`'s existing `InterpolationMethod` — no new classification invented. `path` reuses `PathMorphSolver.morph` directly (Phase 7.4); `slerp` reuses `Scene3DEngine.quaternionSlerp` directly (Phase 8.1). `color` is new: `color.ts` implements sRGB ⇄ OKLab (Björn Ottosson's constants, the same ones behind CSS Color 4's `oklab()`) and mixes in OKLab space rather than naïve sRGB channel lerp, which desaturates through the middle of a mix. `clipPath` interpolates same-named shape functions' numeric arguments (`inset()`, `circle()`, …); anything it can't parse — like `color`'s unparseable keywords (`currentColor`, named CSS colours outside hex/rgb()) — falls back to a discrete hold rather than throwing, since a malformed authored value should degrade, not crash the kernel. `gradient` pairs stops by index when both sides have the same count.

## 5. `evaluate()` (9.3): the composition order, and what's deliberately not in it yet

`evaluate(doc, compositionId, layerId, t, inputs)` implements: base props → state → clips (by grammar §6.2 priority, via Phase 8's `CLIP_TYPE_TO_CATEGORY`) → behaviours → Single Transform Authority synthesis (reusing `EngineAdapters.ts`'s existing `synthesizeSingleTransformMatrix`, not a new one). Clip sampling uses `compositions.ts`'s `clipTimeInComposition` for every timing question (delay, repeat, direction, layer bars, nesting) — Phase 9 does not re-derive composition time math Phase 46 already got right.

**The behaviours slot is real but intentionally thin.** `motion.ts`'s own header comment says it plainly: "the evaluation kernel is Phase 9, the state machine Phase 11, **the behaviour runtime Phase 12**." Only `loop` is evaluated here — it is a pure function of `t` (cycle a property between two values on a period), so it fits a stateless kernel cleanly. `follow-pointer`, `magnet`, `tilt`, `proximity`'s optional spring, `spring-to`, `inertia` and `noise` all respond to a *path* of pointer/scroll input, not a single sample at time `t` — a spring's value depends on its forcing history, which is exactly what the Deterministic Replay Law (Phase 64, its own future decision record) exists to make correct. Implementing them as if they were stateless would produce a function that looks pure but is quietly wrong the moment two evaluate() calls at different `t` don't happen to be visited in time order (exactly what scrubbing backward does). Named in `KERNEL_GAPS`, not silently faked. This is also **AUD-48**'s exact concern ("the kernel's purity assumption doesn't cover stateful effects") — Phase 9 ships a genuinely pure `evaluate()` for what it covers, and documents the rest as Phase 64's job rather than closing AUD-48 by definition-shrinking.

Signal bindings (`doc.bindings`, Phase 60) are the same shape of gap: the v3.0 amendment slots them in after behaviours and before STA synthesis, but Phase 60 doesn't exist yet (the execution order, `DOCS/order.md`, runs it after Phase 9).

## 6. What Phase 9 does not touch: `MotionSequencer.tsx`

The v2.1 amendment text says `evaluate()` "replaces `interpolateTrackValue` in `MotionSequencer.tsx`, which ignores easing." That component (`scrubPatch.ts`'s `interpolateTrackValue` + `scrubStylesForTracks`) operates on the pre-Phase-7 `ElementAnimationTrack`/`PropertyDelta` shape, not `doc.clips` — the same kind of document-disconnected legacy UI Phase 8 found in `ContentBrowser.tsx`. Decision 0004 §3 already named this component explicitly as "the legacy Sequencer, retired in Phases 23/57", kept alive only by value coercion until those phases replace it. Wiring `evaluate()` into a component two phases away from deletion, through a bespoke adapter for a data model it doesn't share with the rest of the document, isn't a good use of this phase's scope — left for whichever of 23/57 actually rebuilds that panel against `doc.clips`.
